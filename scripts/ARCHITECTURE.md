# Scripts — архитектура

## Запросы к Overpass (utils/overpass_handler.py)

Все скрипты ходят в Overpass через `OverpassHandler.get_data`. Попытки чередуются между основным и резервным инстансом (по 5 на каждый, пауза 1 с) — так ни один инстанс не получает повтор сразу после своего же отказа. Внешних ретраев в скриптах быть не должно. В запросах объявляется `[maxsize]` — диспетчер Overpass допускает запрос по заявленным `timeout`/`maxsize`, и меньшие значения повышают шанс получить слот под нагрузкой. Клиентский таймаут = объявленный в запросе `[timeout:N]` + 30 с (без объявления — серверный дефолт 180 с + 30): ожидание слота в очереди сервер в свой `timeout` не засчитывает. Поэтому `[timeout]` в рукописных запросах можно менять свободно — клиент подстроится.

## make_routes_files.py

**Что производит:** `routes-list.js` (используется фронтом для отрисовки карты) и `routes.json` (используется для генерации статических страниц маршрутов).

**Источник данных:** Google Sheets через `GeoRoutesExcelHandler`. Названия станций в маршруте не хранятся — Hugo-шаблон берёт их из `data/stations.json` по коду станции. Таблица содержит два типа листов:
- лист `routes` — главный список всех маршрутов с метаданными;
- отдельные листы с номером маршрута в названии (например, `11`) — расписание конкретного маршрута со станциями и временем.

---

### Логика работы

**1. Фильтрация маршрутов**

Скрипт проходит по всем строкам листа `routes`. Маршруты с `show_on_site = 'n'` пропускаются полностью — они не попадают ни в какой выходной файл. Остальные обрабатываются вне зависимости от поля `active`.

**2. Метаданные маршрута**

Для каждого маршрута собираются:
- названия на трёх языках (ka/en/ru) — из них вырезаются паттерны вида «Поезд №11:», «Train #11:» и т.д.;
- флаги: `active`, `complete`, `online`, `online_tickets_current_site`, `online_tickets_new_site`;
- `frequency` — текстовое описание периодичности (например, «ежедневно»), пустая строка → `null`;
- `start_date` и `end_date` — даты начала/окончания сезонных или через-день маршрутов, хранятся как Unix timestamp в миллисекундах (UTC); могут быть `null`;
- `train_type` — тип поезда, пустая строка → `null`;
- `operator` — `agency_id` оператора поезда (`GR`, `AR`, `SCR`), пустая строка → `null`. Используется GTFS-генератором (`agency.txt`, `routes.agency_id`); у активных маршрутов должен быть одним из агентств в `scripts/gtfs/config.py` (проверяется тестом);
- `has_arrival_time` — флаг, влияет на то, в каком формате хранится расписание в листе маршрута.

**3. Станции и расписание**

Если у маршрута есть отдельный лист — из него берутся станции с временем. Неактивный маршрут без листа допустим — он попадёт в выходной файл без `stations`. Активный маршрут без листа — ошибка.

Для каждой станции:
- в данных хранится только код (английское название, нижний регистр, без пробелов); названия на трёх языках Hugo-шаблон берёт из `data/stations.json` по коду;
- роль: `start` (первая), `end` (последняя), `middle` (все остальные);
- время: для части поездов в таблице одно поле `time` (время стоянки неизвестно), для части — `departure_time` и `arrival_time`. Это несовершенство исходных данных. В первом случае `arrival_time` и `stop_time` будут `null`. Во втором — `stop_time` вычисляется как разница между прибытием и отправлением в минутах. `has_arrival_time` сигнализирует шаблону, какой формат использовать. Если время отсутствует — ставится `-`.
- `-` в таблице означает одно из двух: на первой станции нет прибытия, на последней нет отправления; либо на промежуточной станции поезд точно останавливается, но время неизвестно. Во втором случае у поездов с прибытием и отправлением ставится `-` в обе колонки (`stop_time` → `null`). На конечных станциях время должно быть всегда — это проверяет `test_terminal_stations_have_time`. Сайт выводит `-` как есть, то есть прочерком.

**4. Время в пути**

`travel_time` вычисляется только для маршрутов с `active = 'y'`. Берётся время отправления с первой станции и прибытия (или отправления, если `arrival_time` у второй станции `null`) на последней. Результат — строка формата `HH:MM`. Если данных нет — `-`.

**5. Цена**

Из четырёх возможных полей (`price_2_class`, `price_1_class`, `price_business`, `price_standard`) берутся только непустые. Если значений нет — `null`. Если одно — `{"price_type": "exact", "price": X}`. Если несколько — `{"price_type": "from", "price": MIN}` (минимальная из заполненных).

**6. Маршруты-аналоги**

Колонка `analogue` — ссылки на другие маршруты того же направления: пустая строка или числа через запятую. В выходной файл попадают только те аналоги, чей маршрут сам является `active = 'y'`. Неактивные аналоги молча отбрасываются.

**7. Сортировка и вывод**

Итоговый массив маршрутов сортируется по номеру (`ref`) и записывается в оба выходных файла. В `routes-list.js` добавляется JS-заголовок `export const routes = `.

**Порядок запуска:** `make_stations_files` читает `routes.json` для построения поля `routes` каждой станции, поэтому `make_routes_files` должен запускаться первым.

## make_routes_geo_files.py

**Что производит:** набор JSON-файлов в `static/data/routes_geodata/`, по одному на каждый маршрут. Каждый файл содержит геоданные маршрута из OSM — координаты линий и остановок. Используются фронтом для непосредственной отрисовки маршрутов на карте.

**Источники данных:** Google Sheets (список маршрутов) + Overpass API (геоданные).

---

### Логика работы

**1. Какие маршруты обрабатываются**

Берутся только **активные** маршруты (`active = 'y'`) из листа `routes`.

**2. Запрос к Overpass**

Все OSM-идентификаторы активных маршрутов запрашиваются за один батч-запрос. Overpass возвращает данные в формате GeoJSON-подобного JSON с полной геометрией (`out geom`).

**3. Сохранение и очистка файлов**

Каждый маршрут сохраняется в отдельный файл. Имя файла — **OSM relation ID** маршрута (не номер маршрута `ref`), например `12345678.json`. Файл перезаписывается только если содержимое изменилось — это позволяет видеть в логе что реально обновилось за запуск.

После записи скрипт удаляет из папки все `.json`-файлы, чей OSM ID не входит в список активных маршрутов. Если Overpass вернул меньше маршрутов, чем ожидалось, скрипт выводит предупреждение — старый файл при этом остаётся.

## make_stations_files.py

**Что производит:** `stations-list.js` (используется фронтом для отрисовки станций на карте) и `stations.json` (используется `make_routes_files.py` для получения названий станций).

**Источники данных:** Overpass API (список станций и их координаты), `routes.json` (маршруты через каждую станцию), `stations.json` (существующие описания станций), `station_gr_codes.json` (коды ГЖД).

**Важная зависимость:** скрипт читает `routes.json`, поэтому `make_routes_files.py` должен быть запущен первым.

**Уровень станции (`tier`) и значок (`icon`).** Это два независимых поля: Батуми Центральный — главная станция с пальмой.
- `main` — только из ручного списка в `data/station_meta.json`. Из данных главные станции не выводятся: по числу маршрутов первыми оказались бы пригородные станции Тбилиси.
- `halt` — вычисляется: станция есть в активных маршрутах, но ни в одном нет её времени (ГЖД время не публикует). Если ГЖД начнёт публиковать время, станция сама станет `regular`. Станция, у которой время есть хотя бы в одном маршруте, — `regular`. Для исключений можно задать `tier` в `station_meta.json`, он важнее вычисленного.
- `regular` — все остальные, в том числе станции без активных маршрутов.
- `icon` (`star`, `beach`, `airport`) — тоже из `station_meta.json`, выбирает значок маркера на карте.

Коды в `station_meta.json`, которых нет в `stations.json`, валят тест (`test_station_meta_codes_exist`): опечатка иначе молча оставила бы станцию без уровня.

Где используется: на карте главные крупнее, платформы мелкие, а на главной без выбранного маршрута видны только с `HALTS_MIN_ZOOM` (`static/js/constants.js`); список станций разбит на три группы (`layouts/_default/stations-list.html`); на странице платформы перед расписанием — пояснение, что время не публикуется (`layouts/shortcodes/single-station.html`, `tier` передаётся в параметры страницы в `content/stations/_content*.gotmpl`).

---

### Логика работы

**1. Какие станции попадают в список**

Список станций не берётся из таблицы напрямую. Вместо этого:
- одним запросом к Overpass для всех маршрутов с `show_on_site = 'y'` берутся их stop-ноды (`role = 'stop'`) вместе с тегами и координатами — без геометрии самих маршрутов (`OverpassHandler.get_route_stops_data`).

Таким образом, источник правды о составе станций — **OSM**, а не таблица.

**2. Названия и код станции**

Для каждой станции берутся `name:en`, `name:ka`, `name:ru` из OSM-тегов. Если тег отсутствует — подставляются заглушки («unknown station» и т.д.).

Код станции (`code`) — это английское название, приведённое к нижнему регистру, без пробелов и дефисов. Именно этот код используется везде как идентификатор станции.

Код зависит от `name:en`, а в листах маршрутов в Google Sheets коды станций записаны вручную. Поэтому если поменять `name:en` в OSM, у станции сменится код, и в листах маршрутов его нужно поменять тоже. От кода зависят также URL страницы станции (`/stations/<code>/`), `stop_id` в GTFS и `STOP_TIMEZONES` в `scripts/gtfs/config.py`.

Если у двух OSM-нод одинаковый code (например, дублирующиеся узлы одной платформы), они объединяются в одну запись с массивом `id`.

**3. Тип станции**

Тип определяется жёстко по коду:
- `tbilisicentralstation` → `main`
- `batumicentral` → `beach`
- `kutaisiinternationalairport` → `airport`
- все остальные → `secondary`

**4. Код ГЖД**

Для каждой станции ищется числовой код в `station_gr_codes.json` (сопоставление по `name:en`). Для ряда станций, у которых название в OSM не совпадает с названием в справочнике ГЖД, есть жёстко прописанный словарь исключений (`exceptional_stations`). Если код не найден — ставится `00000`.

**5. Описания станций**

Описания не хранятся в Google Sheets и не приходят из OSM. Их первоисточник — само `stations.json`. Перед перезаписью файла скрипт читает из него существующие описания и добавляет их обратно в новые данные. Без этого шага описания бы терялись при каждом обновлении.

**6. Маршруты через станцию**

Из уже готового `routes.json` строится словарь: для каждой станции — какие маршруты через неё проходят и в какой роли (`departure` / `arrival` / `via`), с временем отправления/прибытия. Эти данные добавляются в запись станции как поле `routes` и используются на страницах станций.

**7. Сортировка и вывод**

Массив станций сортируется по `name_en` и записывается в оба файла. В `stations-list.js` добавляется JS-заголовок `export const stations = `.

## make_railway_network_file.py

**Что производит:** `static/js/components/railway-network/railway-network-data.js` — GeoJSON с полной геометрией всей железнодорожной сети Грузии. Используется фронтом для отрисовки сетки дорог на карте в виде фонового слоя.

**Источник данных:** Overpass API.

---

### Логика работы

Один запрос к Overpass запрашивает все way с тегом `railway=rail` в пределах Грузии, исключая промышленные ветки, тупики и сортировочные пути (фильтры `usage!=industrial`, `service!=spur/yard/siding`). Область задаётся по ID (`area(id:3600028699)` = relation Грузии 28699 + 3600000000), а не по имени — поиск по имени дороже и может совпасть не только со страной. Вывод — `out skel geom`: только геометрия, без тегов, т.к. фронт свойства объектов не использует. Overpass возвращает свой JSON-формат (`[out:json]`), который конвертируется в GeoJSON вручную. Ради размера файла (~2 МБ → ~0,35 МБ) way упаковываются в фичи `MultiLineString` — по одной на стиль отрисовки, координаты округляются до 5 знаков (~1 м), JSON пишется без отступов.

**Кукушка** (Боржоми — Бакуриани, узкоколейка, поэтому в `railway=rail` не попадает) запрашивается в том же запросе отдельным множеством `way["railway"]["wikidata"="Q3650431"]` и вычитается из основного, чтобы общий way не нарисовался дважды. Основная сеть выводится через `out skel` (без тегов), Кукушка — через `out geom` (с тегами), и в Python way разделяются по тегу `wikidata`. Кукушка идёт второй фичей с `properties: {"kind": "kukushka"}` (последней — чтобы рисовалась поверх), основная сеть — первой, без properties. Фронт (`RailwayNetwork.js`) красит её синим через выражение по `kind` в том же слое; в «тени» (выбран маршрут) серая вся сеть, включая Кукушку. Если Overpass Кукушку не вернул, фича не пишется и выводится предупреждение. Новый особый стиль добавляется так же — отдельной фичей со своим `kind`. Ретраи — в `OverpassHandler`, как у остальных скриптов.

**Запускается вручную** по мере необходимости (данные OSM меняются редко).

## check_all_routes.py

**Что делает:** инструмент ручной проверки — сравнивает список станций на каждом маршруте в таблице и в OSM, выводит расхождения в терминал. Ничего не записывает и не изменяет.

**Источники данных:** Google Sheets (локальные данные о станциях маршрута) + Overpass API (актуальные данные из OSM).

---

### Логика работы

Запускается в CI перед `make_routes_geo_files.py`. Расхождения выводятся в лог, но не останавливают билд.

Скрипт проходит по всем **активным** маршрутам с листом в таблице (`active = 'y'`) и за один лёгкий батч-запрос к Overpass (relations без геометрии + их stop-ноды) сопоставляет списки станций:

- **локальный** — коды станций из листа маршрута в таблице;
- **актуальный** — коды станций, полученные из OSM через Overpass: берётся relation маршрута, из его members извлекаются узлы с `role = 'stop'`, их `name:en` превращается в коды.

Если списки совпадают — маршрут помечается как OK. Если нет — выводятся две группы расхождений:
- станции, которые есть только в таблице (возможно, удалены из OSM или переименованы);
- станции, которые есть только в OSM (возможно, добавлены в OSM, но не занесены в таблицу).

**Порядок станций не проверяется** — только состав. Маршруты без листа в таблице автоматически пропускаются. Если все маршруты консистентны — выводится одно итоговое сообщение; при расхождениях — детали по каждому проблемному маршруту.

## make_gtfs.py

**Что производит:** GTFS-фид — txt-файлы в `build/gtfs/` и архив `static/gtfs/georgian-railway.zip`, который публикуется вместе с сайтом. Ни то, ни другое не коммитится: фид зависит от даты сборки (окно «сегодня + 6 месяцев»).

**Источники данных:** `data/routes.json`, `data/stations.json`, `static/data/routes_geodata/` (геометрия для `shapes.txt`). Google Sheets и Overpass не читает.

**Порядок запуска:** после `make_routes_files`, `make_stations_files` и (для актуальных форм) `make_routes_geo_files`. В CI — через `.github/actions/gtfs-feed` вместе с валидатором.

Маппинг полей и все решения — в `scripts/GTFS.md`.

## make_share_images.py

**Что производит:** картинки-превью для шеринга ссылок (`og:image`, 1200×630) в `static/images/share/`:
- `home-<lang>.png` — главная, по одной на язык (на ней текст). Она же — картинка по умолчанию для всех страниц без своей (`languages.<lang>.params.images` в `hugo.yaml`);
- `routes-list.png` — список маршрутов: все пассажирские линии красным (подключена в `images` front matter `content/routes/_index*.md`);
- `routes/<ref>.png` — активные маршруты: маршрут красным, начальная и конечная станции;
- `stations/<code>.png` — станции внутри Грузии: точка станции.
- `stations-list.png` — список станций: все станции внутри Грузии маленькими красными точками (подключена в `images` front matter `content/stations/_index*.md`);
- `trains/<train_type>.jpg` — страницы поездов: обложка (`cover` из `assets/images/trains/<train_type>/photos.yaml`), обрезанная по центру до 1200×630; JPEG, т.к. это фото;
- `trains-list.jpg` — список поездов и поезда без фото: коллаж 2×2 из обложек первых четырёх поездов по `weight`.

Картинки поездов подключены строкой `images:` во front matter каждой языковой версии (`content/trains/*/index*.md`, `_index*.md`). `cover` и `weight` читаются регуляркой, а не YAML-парсером (PyYAML нет в зависимостях): обе — простые строки верхнего уровня. Новая обложка или другой порядок поездов не перерисовываются сами — удалить файл или `--force`.

На картинках маршрутов и станций текста нет (одна картинка на все языки): какая это страница, говорят заголовок и описание рядом с картинкой в превью.

**Источники данных:** `data/routes.json`, `data/stations.json`, `static/data/routes_geodata/`, контур Грузии из `share_images/basemap.json`. Google Sheets и Overpass не читает.

**Порядок запуска:** после `make_routes_files`, `make_stations_files` и `make_routes_geo_files`.

**Картинки коммитятся и не перерисовываются.** По умолчанию скрипт рисует только недостающие (новый маршрут или станция), а общие части (линии, фон) считает, только если есть что рисовать. В CI он запускается в каждом workflow деплоя, и шаг коммита данных (`pages.yaml`, `pages-fast.yaml`) коммитит добавленные картинки вместе с остальными данными. `--force` перерисовывает всё — после изменения стиля. Если у маршрута поменялся путь, достаточно удалить его файл. Картинки удалённых маршрутов и станций не удаляются (на них просто никто не ссылается).

Hugo подключает картинку маршрута или станции, только если файл есть (`fileExists` в `content/{routes,stations}/_content*.gotmpl`), иначе страница получает картинку главной.

### Логика и решения

- **Стиль:** только силуэт Грузии (без соседей), белый с мягкой тенью на холодном светлом фоне; пассажирские линии серым, предмет страницы — красным, как на логотипе. На главной силуэт обрезан правым краем, на маршрутах и станциях — целиком, логотип с названием в пустом юго-западном углу.
- **Линии — только пассажирские:** объединение путей всех активных маршрутов из `routes_geodata`, а не вся сеть из `railway-network-data.js`: на всей сети множество тупиков, веток и подъездных путей выглядят как грязь. Линии обрезаются по границе Грузии (международные маршруты уходят в Армению и Азербайджан, соседей на картинке нет).
- **Сглаживание:** OSM-way сначала склеиваются в непрерывные линии (`merge_lines`), иначе на каждом стыке излом. Затем точки ставятся равномерно и усредняются скользящим окном (`resample` + `smooth`). Дуглас — Пекер для этого не годится: у двухпутных участков он выбирает разные точки на каждом пути, и они расходятся в две линии. Короткие тупики выкидываются (`drop_stubs`), тупик определяется по расстоянию до других линий, а не по точному совпадению координат — стыки в OSM не всегда точные.
- **Маршрут** обрезается у конечных станций (`trim_at`): в OSM-отношении маршрута бывают пути дальше станции. Крючок у Озургети — настоящая география (ветка идёт сначала на запад к Натанеби).
- **Отрисовка:** Pillow. Он не сглаживает фигуры, поэтому всё рисуется в `SUPERSAMPLE` раз крупнее и уменьшается усреднением (`reduce`, LANCZOS в разы медленнее). Широкая линия из тысяч мелких отрезков у Pillow выходит с рваными краями, поэтому перед отрисовкой точки прореживаются. Тень суши размывается на итоговом размере (размытие крупной картинки медленное). Фон с сушей, серыми линиями и логотипом рисуется один раз и копируется для каждой картинки.
- **Сохранение:** палитра 256 цветов, метод median cut — вдвое меньше файл (~30–50 КБ). Метод по умолчанию (octree) даёт полосы в тени и окрашивает белую сушу.
- **Шрифты** — в `share_images/fonts/` (OFL, лицензии рядом): Onest для латиницы и кириллицы, Noto Sans Georgian для грузинского (в Onest грузинского нет). Вариативные, вес задаётся через `set_variation_by_axes`. Тексты главной — `HOME_TEXT` в `render.py`.

## make_share_basemap.py

**Что производит:** `scripts/share_images/basemap.json` — контур Грузии для картинок-превью, упрощённый под кадр. Коммитится, поэтому CI не скачивает исходник.

**Источник данных:** Natural Earth `ne_10m_admin_0_countries` (общественное достояние, атрибуция не нужна). Грузия там в международно признанных границах (с Абхазией и Цхинвальским регионом), одним полигоном. Границы из OSM не подходят: граница страны в OSM проведена по морю (территориальные воды), а не по берегу.

**Запускается вручную**, только при изменении кадра в `share_images/frame.py` (размер 1200×630, границы, Web Mercator): контур упрощается под конкретный кадр. Хранится в lon/lat. `--preview <png>` дополнительно рисует контур отдельно.
